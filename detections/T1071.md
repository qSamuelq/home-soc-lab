## 1. Attack simulation

Atomic Red Team test **T1071.001-2 — "Malicious User Agents - CMD"**.

```
Invoke-AtomicTest T1071.001 -TestNumbers 2
```

Each execution makes four HTTP requests, each with a different user agent string
associated with known malware:

```
Curl.exe -s -A "HttpBrowser/1.0" -m3 www.google.com >nul 2>&1
Curl.exe -s -A "Wget/1.9+cvs-stable (Red Hat modified)" -m3 www.google.com >nul 2>&1
Curl.exe -s -A "Opera/8.81 (Windows NT 6.0; U; en)" -m3 www.google.com >nul 2>&1
Curl.exe -s -A "*<|>*" -m3 www.google.com >nul 2>&1
```

The technique simulates an infected host beaconing to command and control
infrastructure. Malware frequently identifies itself with a user agent that does not
correspond to any real browser — either a hardcoded default left in by the implant's HTTP
library (`HttpBrowser/1.0` is associated with a known RAT), an outdated browser string, or
placeholder junk that was never replaced (`*<|>*`).

No prerequisites were needed: `curl.exe` ships with Windows 11 at
`C:\Windows\System32\curl.exe`. There is no cleanup step — nothing persists.

## 2. The visibility gap — the main finding for this technique

**The defining characteristic of this technique is not observable in this lab's telemetry.**

A user agent is sent inside the HTTP request. Sysmon observes the operating system:
processes starting, files written, sockets opened. It does not inspect the contents of
a connection. The atomic's own description says to use Wireshark to observe the result,
which is an acknowledgement that the signal lives above the layer Sysmon records.

Two independent blind spots were confirmed, not one.

### Blind spot 1 — the HTTP layer

Sysmon Event ID 3 (Network Connection) records source and destination IP, ports, protocol
and the responsible process. There is no field for HTTP headers. At that layer, a beacon
using `HttpBrowser/1.0` and a legitimate HTTPS request are identical.

### Blind spot 2 — the Sysmon config never logged the connections at all

Running the attack produced **four process-creation events and zero network-connection
events**:

```kql
// EventCategory 1 — returned 4 curl.exe events plus the cmd.exe parent
Event | where Source contains "Sysmon" | where EventCategory == 1
| where ParameterXml contains "curl.exe"

// EventCategory 3 — returned nothing
Event | where Source contains "Sysmon" | where EventCategory == 3
| where ParameterXml contains "curl.exe"
```

The cause is in the SwiftOnSecurity Sysmon config. Its `NetworkConnect` section uses
`onmatch="include"`, meaning connections are logged **only** from an explicit allowlist of
paths:

```xml
<NetworkConnect onmatch="include">
  <Image name="Usermode" condition="begin with">C:\Users\</Image>
  <Image name="Caution"  condition="begin with">C:\Recycle</Image>
  <Image              condition="begin with">C:\ProgramData</Image>
  <Image              condition="begin with">C:\Windows\Temp</Image>
  ...
</NetworkConnect>
```

`curl.exe` runs from `C:\Windows\System32\`, which is not on that list, so its network
activity was never recorded. The config's own comment states it takes a deliberately
conservative approach to network logging, limited to high-signal events only.

This is a realistic constraint rather than a misconfiguration — logging every network
connection on every endpoint is prohibitively expensive. But it means **a signed
system binary being abused for C2 is invisible in network telemetry on this host**, which
is precisely the living-off-the-land pattern the config is otherwise designed to catch.

### What would actually be needed

| Telemetry             | What it would give                                                                       |
| --------------------- | ---------------------------------------------------------------------------------------- |
| Web proxy logs        | User agent strings, full URLs, request/response sizes                                    |
| Zeek / network sensor | HTTP metadata including user agent, without full packet capture                          |
| TLS inspection        | Visibility into HTTPS request contents                                                   |
| Sysmon config change  | Broaden `NetworkConnect` to include `C:\Windows\System32\`, at a significant volume cost |

## 3. Detection rule

Given the above, the detection is built on **process creation** rather than network
telemetry — it detects the command-line form of the technique, which is what this sensor
can actually see.

Rule name: **T1071.001 – Command-Line HTTP Client with User Agent Override**
Severity: Medium · Run every 10 minutes · Lookback 10 minutes
Entity mapping: Host → HostName → `Computer`

```kql
Event
| where Source contains "Sysmon"
| where EventCategory == 1
| where ParameterXml matches regex @"(?i)<Param>\d+</Param><Param>[^<]*\\(curl|certutil|wget)\.exe</Param>"
| where ParameterXml matches regex @"(?i)\s-A\s+""[^""]+"""
```

### Design decisions

**Behaviour over IOC list.** The obvious rule matches the four user agent strings the
atomic uses. That was rejected: it detects one specific test, and an attacker changing a
single string defeats it entirely. Matching instead on _a command-line HTTP client being
given an explicit user agent override_ describes the tradecraft rather than one sample of
it. Legitimate manual use of `-A` on an endpoint is rare.

**XML escaping would have broken the IOC list anyway.** `ParameterXml` stores XML-escaped
content, so the atomic's `*<|>*` user agent is stored as `*&lt;|&gt;*`. A literal
`has_any("*<|>*")` filter would never have matched — a silent failure that would have gone
unnoticed because the other three strings still fired. The same escaping is visible
elsewhere in this lab's data, e.g. `>nul 2>&1` stored as `&gt;nul 2&gt;&amp;1`.

**Position-anchored image match.** As established in the T1547.001 case file, the flat
`ParameterXml` blob makes plain string matching unreliable. Requiring the binary name to
appear in the parameter immediately following the numeric PID pins the match to the image
field rather than anywhere the string happens to appear.

### Stated coverage gap

This rule detects the **command-line form only**. Real malware makes its HTTP requests
from inside its own process using an HTTP library — there is no command line to inspect,
and the user agent never touches disk or the process table. Such an implant would not
match this rule, and given blind spot 2 above, may generate no network telemetry either.

The honest summary: **this lab can detect the test, but not the technique.** Closing that
gap requires network-layer telemetry, not a better query.

## 4. False positive analysis

No false positives were observed during testing. `curl.exe` with an explicit `-A` flag did
not occur in normal background activity on this host.

Expected benign sources in a production environment:

- Developers and administrators testing web endpoints manually
- Build and CI scripts using `curl -A` to identify themselves to APIs
- Monitoring and health-check scripts
- Software installers using `certutil` to fetch components

The narrow scope keeps volume low, but on a developer workstation this rule would be
considerably noisier than on a general-purpose endpoint. Tiering by host role would be the
first tuning step in production.

## 5. Tuning — before and after

Same two-stage method as the other techniques in this repo. Identical three-execution
batch run twice, changing only the two grouping settings.

```powershell
Invoke-AtomicTest T1071.001 -TestNumbers 2
Start-Sleep 20
Invoke-AtomicTest T1071.001 -TestNumbers 2
Start-Sleep 20
Invoke-AtomicTest T1071.001 -TestNumbers 2
```

```kql
SecurityIncident
| where CreatedTime > ago(20m)
| where Title contains "User Agent"
| summarize arg_max(TimeGenerated, *) by IncidentNumber
| summarize Incidents = count()
```

### Results

|                   | Event grouping          | Alert grouping                            | Executions | Events | Incidents |
| ----------------- | ----------------------- | ----------------------------------------- | ---------- | ------ | --------- |
| **Before tuning** | Trigger alert per event | Disabled                                  | 3          | 12     | **12**    |
| **After tuning**  | All events → one alert  | Enabled, 1 day, all alerts → one incident | 3          | 12     | **1**     |

**Reduction: 12 incidents → 1 for identical attacker activity — a 92% drop, the largest
in this repo.**

This technique produces the highest event-to-execution ratio of any tested here: each
execution fires four separate `curl.exe` processes, so a single simulated beaconing burst
generated twelve incidents untuned. A real implant beaconing every 60 seconds would
generate an unusable volume without grouping, which makes this the clearest demonstration
of why incident grouping matters operationally rather than cosmetically.
