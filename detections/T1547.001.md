# T1547.001 — Boot or Logon Autostart Execution: Registry Run Keys

| Field            | Value                                                                       |
| ---------------- | --------------------------------------------------------------------------- |
| ATT&CK ID        | T1547.001                                                                   |
| Tactics          | Persistence (TA0003), Privilege Escalation (TA0004)                         |
| Platform         | Windows                                                                     |
| Host             | `win-11-SIEM` (Windows 11, VirtualBox)                                      |
| Telemetry source | Sysmon Event ID 13 (Registry value set) → AMA → Log Analytics `Event` table |
| SIEM             | Microsoft Sentinel (`Home-soc-workspace`)                                   |
| Date tested      | 2026-09-12                                                                  |

---

## 1. Attack simulation

Atomic Red Team test **T1547.001-1 — "Reg Key Run"**.

```
Invoke-AtomicTest T1547.001 -TestNumbers 1
```

Command executed:

```
REG ADD "HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Run" /V "Atomic Red Team" /t REG_SZ /F /D "C:\Path\AtomicRedTeam.exe"
```

This writes a value to the current user's Run key so the named binary executes at every
logon — the most common form of userland persistence on Windows.

**Note on repeat runs:** `-Cleanup` must be run between executions. Re-writing an
identical value may not generate a fresh `SetValue` event, so consecutive runs without
cleanup produce fewer events than expected.

---

## 2. Telemetry validation — a new event type

This is the first technique in this lab detected from **registry telemetry** rather than
process creation. Sysmon writes two relevant event types:

| Event ID | EventCategory | Meaning                      |
| -------- | ------------- | ---------------------------- |
| 12       | 12            | Registry key create / delete |
| 13       | 13            | Registry **value set**       |

Event ID 13 is the one that matters here, because it carries the **value data** — the path
the persistence actually points at. Event ID 1 (process creation) shows `reg.exe` running
with its command line, but registry telemetry shows the resulting state change directly,
which also catches techniques that write the key without spawning a process at all.

Baseline volume check before writing anything:

```kql
Event
| where TimeGenerated > ago(54h)
| where Source contains "Sysmon"
| summarize count() by EventCategory
```

Returned 1,028 Event ID 13 events over ~54 hours (~19/hour) against 1,825 process-creation
events. Registry telemetry is high volume, so an untargeted rule here would be unusable.

### Field layout in `ParameterXml`

As with all Sysmon data in the `Event` table, every field is flattened into one unlabelled
`ParameterXml` blob. For Event ID 13 the ordering is:

```
<Param>Sysmon rule name</Param>      e.g. "T1060,RunKey"
<Param>SetValue</Param>              event type
<Param>timestamp</Param>
<Param>{process GUID}</Param>
<Param>PID</Param>
<Param>IMAGE — the process doing the writing</Param>
<Param>target registry key path</Param>
<Param>value data — what the persistence points at</Param>
<Param>user</Param>
```

**Config observation:** the first parameter is the Sysmon config's own rule name, and the
SwiftOnSecurity config already tags Run key writes as `T1060,RunKey` (T1060 being the
retired ATT&CK ID for this technique). A detection could key off that tag directly, but
that was deliberately avoided — it would make the rule dependent on one specific Sysmon
config rather than on the registry path itself, and would silently break on any host
running a different config.

## 3. The false positive problem

Run key writes are **routine**. Over 48 hours on an idle two-VM lab, legitimate software
wrote to Run keys 10 times, in bursts rather than on a schedule:

| Source                                                   | Behaviour                                   |
| -------------------------------------------------------- | ------------------------------------------- |
| `C:\Program Files (x86)\Microsoft\Edge\Application\...`  | Edge updater writing autostart entries      |
| `C:\Users\vboxuser\AppData\Local\Microsoft\OneDrive\...` | OneDrive writing `RunOnce\Uninstall` values |

### The naive tuning approaches both fail

The obvious move — borrowed from this lab's T1053.005 rule — is to match on the _value
data_ pointing at a script interpreter, since malware usually persists something like
`cmd.exe` or `powershell.exe` rather than a signed binary. That fails here. One of the
OneDrive writes sets:

```
HKU\...\CurrentVersion\RunOnce\Uninstall 26.153.0809.0004
  → C:\WINDOWS\system32\cmd.exe /q /c rmdir /s /q "C:\Users\vboxuser\...\OneDrive\26.153.0809.0004"
```

That is a Run key entry, pointing at `cmd.exe`, executing a delete, from a user AppData
path. It matches every heuristic that would normally flag malicious persistence — and it
is entirely legitimate cleanup by Microsoft's own software.

Matching on user-writable paths fails for the same reason: OneDrive lives in AppData, so
"persistence written from a user profile directory" describes both the attack and the
benign case.

### What actually separates them

The distinguishing factor is not _what_ is persisted but **what process performs the
write**. Legitimate installers and updaters write registry values through the Windows API
from their own binaries. The attack shells out to `reg.exe`.

### The flat-blob obstacle

A first attempt using `has_any` failed:

```kql
| where ParameterXml has_any ("reg.exe", "powershell.exe", "cmd.exe", ...)
```

This returned 5 results over 48 hours — the atomic **plus all four OneDrive writes** —
because `has_any` searches the entire flattened blob and `cmd.exe` appears in OneDrive's
_value data_ field, not its image field. The blob format means a plain string match cannot
distinguish "the process that wrote this" from "the thing that was written".

The fix is to anchor on **field position**. The writing process is always the parameter
immediately following the numeric PID:

```kql
| where ParameterXml matches regex @"(?i)<Param>\d+</Param><Param>[^<]*\\(reg|powershell|pwsh|cmd|wscript|cscript|mshta)\.exe</Param>"
```

`[^<]*` cannot cross a `<Param>` boundary, and requiring a numeric parameter immediately
before it pins the match to the image field specifically.

**Result: 1 match over 48 hours — the atomic test, and nothing else.**

## 4. Detection rule

Rule name: **T1547.001 – Run Key Persistence Written by Script Interpreter**
Severity: Medium · Run every 10 minutes · Lookback 10 minutes
Entity mapping: Host → HostName → `Computer`

```kql
Event
| where Source contains "Sysmon"
| where EventCategory == 13
| where ParameterXml contains @"CurrentVersion\Run"
| where ParameterXml matches regex @"(?i)<Param>\d+</Param><Param>[^<]*\\(reg|powershell|pwsh|cmd|wscript|cscript|mshta)\.exe</Param>"
```

### Known coverage gap — stated deliberately

This rule does **not** detect T1547.001 generally. It detects Run key persistence written
_by an interpreter process_. Malware that writes the same registry value through the
Windows API from its own binary will not match, and neither will autostart techniques
using different keys — for example `Winlogon\Shell` (atomic test 15), which achieves the
same persistence outcome via a registry path this rule does not cover.

This is a deliberate precision-over-coverage trade. On this telemetry, a rule broad enough
to catch all Run key writes fires on Edge and OneDrive several times a day and would be
switched off within a week. A narrow rule that fires once in 48 hours, on real attacker
tradecraft, is worth keeping. The gap is documented rather than hidden, and in production
the right answer is this rule _plus_ separate coverage for other autostart locations,
rather than one broad rule trying to cover everything.

## 5. Tuning — before and after

Same two-stage method established in the T1053.005 case file:

| Stage                  | Setting        | Location              |
| ---------------------- | -------------- | --------------------- |
| Query results → alerts | Event grouping | Set rule logic tab    |
| Alerts → incidents     | Alert grouping | Incident settings tab |

Identical three-execution batch run twice, with cleanup between each execution, changing
only the two grouping settings.

```powershell
Invoke-AtomicTest T1547.001 -TestNumbers 1
Start-Sleep 20
Invoke-AtomicTest T1547.001 -TestNumbers 1 -Cleanup
Invoke-AtomicTest T1547.001 -TestNumbers 1
Start-Sleep 20
Invoke-AtomicTest T1547.001 -TestNumbers 1 -Cleanup
Invoke-AtomicTest T1547.001 -TestNumbers 1
```

```kql
SecurityIncident
| where CreatedTime > ago(20m)
| where Title contains "Run Key"
| summarize arg_max(TimeGenerated, *) by IncidentNumber
| summarize Incidents = count()
```

### Results

|                   | Event grouping          | Alert grouping                            | Executions | Events | Incidents |
| ----------------- | ----------------------- | ----------------------------------------- | ---------- | ------ | --------- |
| **Before tuning** | Trigger alert per event | Disabled                                  | 3          | 3      | **3**     |
| **After tuning**  | All events → one alert  | Enabled, 1 day, all alerts → one incident | 3          | 3      | **1**     |

**Reduction: 3 incidents → 1 for identical attacker activity.**

Note this technique produces **one** event per execution, not two — registry telemetry
records the state change once, whereas the process-creation rules in this repo matched both
the acting process and its parent's command line. The pre-tuning incident count is
therefore lower here than for T1053.005 despite an identical test batch.

## 6. Cleanup

```powershell
Invoke-AtomicTest T1547.001 -TestNumbers 1 -Cleanup
```

Verify the value is gone:

```powershell
Get-ItemProperty "HKCU:\SOFTWARE\Microsoft\Windows\CurrentVersion\Run" -Name "Atomic Red Team" -ErrorAction SilentlyContinue
```
