# T1053.005 — Scheduled Task/Job: Scheduled Task

| Field            | Value                                                                    |
| ---------------- | ------------------------------------------------------------------------ |
| ATT&CK ID        | T1053.005                                                                |
| Tactics          | Persistence (TA0003), Execution (TA0002)                                 |
| Platform         | Windows                                                                  |
| Host             | `win-11-SIEM` (Windows 11, VirtualBox)                                   |
| Telemetry source | Sysmon Event ID 1 (Process Creation) → AMA → Log Analytics `Event` table |
| SIEM             | Microsoft Sentinel (`Home-soc-workspace`)                                |
| Date tested      | 2026-09-10                                                               |

---

## 1. Attack simulation

Atomic Red Team test **T1053.005-2 — "Scheduled task Local"**.

```
Invoke-AtomicTest T1053.005 -TestNumbers 2
```

Command executed:

```
SCHTASKS /Create /SC ONCE /TN spawn /TR C:\windows\system32\cmd.exe /ST 20:10
```

This creates a local scheduled task named `spawn` whose action launches `cmd.exe`.

**Why test 2 and not test 4:** test 4 ("Powershell Cmdlet Scheduled Task") uses
`Register-ScheduledTask`, which is an in-process PowerShell cmdlet. No separate binary is
spawned, so nothing identifying task creation appears in Sysmon Event ID 1 at all —
detecting it would require PowerShell script block logging (Event ID 4104), which is not
configured in this lab. Test 2 uses `schtasks.exe` directly and is visible in the
telemetry already being collected.

**Note on repeat runs:** `schtasks /create` fails if a task of the same name already
exists, so `-Cleanup` must be run between repeated executions or subsequent runs silently
produce no telemetry.

---

## 2. Telemetry validation

Each execution produces **two** matching process-creation events:

1. `schtasks.exe` — the process performing the task creation
2. `cmd.exe` — the parent process, whose own command line contains the full
   `SCHTASKS /Create ...` string

Confirmed with:

```kql
Event
| where TimeGenerated > ago(30m)
| where Source contains "Sysmon"
| where EventCategory == 1
| where ParameterXml contains "schtasks"
| project TimeGenerated, Computer, ParameterXml
| order by TimeGenerated desc
```

Three executions consistently produced six events.

## 3. Detection rule

Rule name: **T1053.005 – Scheduled Task Creation Running Script Interpreter**
Severity: Medium · Run every 10 minutes · Lookback 10 minutes
Entity mapping: Host → HostName → `Computer`

```kql
Event
| where Source contains "Sysmon"
| where EventCategory == 1
| where ParameterXml contains "schtasks"
| where ParameterXml contains "/create"
| where ParameterXml matches regex @"(?i)/tr\s+[^<]*(cmd\.exe|powershell|pwsh|wscript|cscript|mshta|rundll32|regsvr32)"
```

### Design decisions

**Detect the task action, not just task creation.** Scheduled task creation on its own is
extremely common — installers, updaters and management agents all do it. Matching
specifically on tasks whose `/TR` action launches a script interpreter or
living-off-the-land binary is a far stronger indicator of malicious intent and
dramatically reduces the benign match rate.

**`[^<]*` rather than `.*` in the regex.** `ParameterXml` is a single flat blob containing
every Sysmon field concatenated, including `ParentImage`. In this atomic the parent
process _is_ `C:\Windows\System32\cmd.exe`, so `.*` would happily match
`/TR <anything at all> ... cmd.exe` by crossing into a completely different field. That
would fire on a task pointing at an entirely benign target purely because `cmd.exe`
appeared elsewhere in the row. `[^<]*` cannot cross a `<Param>` boundary, so the match is
constrained to the actual `/TR` value.

**Matching `schtasks` without `.exe`.** The parent `cmd.exe` command line contains
`SCHTASKS` in uppercase with no path. KQL `contains` is case-insensitive, so dropping the
extension catches both the process image and the parent command line.

## 4. False positive analysis

Scheduled task creation is routine in a real Windows environment. Expected benign
sources:

- Application installers and updaters (Chrome, Adobe, Java, Windows Update)
- Endpoint management tooling (SCCM, Intune, RMM agents)
- Backup and antivirus software
- Task creation by administrators during legitimate maintenance

The `/TR` interpreter filter removes the large majority of these, because most legitimate
software schedules its own signed executable rather than `cmd.exe` or PowerShell. What
remains is genuinely worth an analyst's attention, but is still not automatically
malicious — plenty of enterprise scripts are scheduled via `cmd.exe` wrappers.

Improvements not implemented in this lab:

- Filter on task creation by non-administrative or non-service accounts
- Correlate with the parent process of `schtasks.exe` (an Office application or browser
  spawning task creation is far more suspicious than an installer)
- Baseline task names and flag ones that do not match known patterns
- Alert on `/RU SYSTEM` specifically, which would extend coverage to the Privilege
  Escalation tactic

## 5. Tuning — before and after

Sentinel applies noise reduction at **two independent stages**, and this technique was
used to measure both together:

| Stage                  | Setting            | Location              | What it does                                                      |
| ---------------------- | ------------------ | --------------------- | ----------------------------------------------------------------- |
| Query results → alerts | **Event grouping** | Set rule logic tab    | Collapses all matching rows from one rule run into a single alert |
| Alerts → incidents     | **Alert grouping** | Incident settings tab | Collapses multiple alerts into a single incident                  |

### Method

Identical three-execution batch run twice, with cleanup between each execution. Only the
two grouping settings changed between runs.

```powershell
Invoke-AtomicTest T1053.005 -TestNumbers 2
Start-Sleep 20
Invoke-AtomicTest T1053.005 -TestNumbers 2 -Cleanup
Invoke-AtomicTest T1053.005 -TestNumbers 2
Start-Sleep 20
Invoke-AtomicTest T1053.005 -TestNumbers 2 -Cleanup
Invoke-AtomicTest T1053.005 -TestNumbers 2
```

Counting query — `SecurityIncident` writes a new row on every incident state change, so
`arg_max` is required to avoid overcounting:

```kql
SecurityIncident
| where CreatedTime > ago(20m)
| where Title contains "Scheduled Task"
| summarize arg_max(TimeGenerated, *) by IncidentNumber
| project IncidentNumber, CreatedTime, AlertCount = array_length(AlertIds)
| order by CreatedTime asc
```

### Results

|                   | Event grouping          | Alert grouping                            | Executions | Events | Incidents         |
| ----------------- | ----------------------- | ----------------------------------------- | ---------- | ------ | ----------------- |
| **Before tuning** | Trigger alert per event | Disabled                                  | 3          | 6      | **6** (1142–1147) |
| **After tuning**  | All events → one alert  | Enabled, 1 day, all alerts → one incident | 3          | 6      | **1** (1148)      |

**Reduction: 6 incidents → 1 incident for identical attacker activity, an 83% drop in
analyst queue volume with no loss of detection coverage.**

Baseline incidents were created at 18:05:42–18:05:43 UTC; the tuned run produced a single
incident at 18:09:28 UTC.

### Why this matters

Both settings reduce noise but at different points, and conflating them produces
misleading tuning numbers. An earlier measurement attempt on this rule appeared to show
grouping working when in fact event grouping had been collapsing six events into one
alert the whole time — the incident count was low for a reason unrelated to the setting
being tested. The only way to get a trustworthy figure was to disable **both** layers,
establish a true baseline, then re-enable both and re-measure with an identical batch.

## 6. Cleanup

```powershell
Invoke-AtomicTest T1053.005 -TestNumbers 2 -Cleanup
Get-ScheduledTask -TaskName "spawn" -ErrorAction SilentlyContinue
```

The second command should return nothing, confirming the persistence mechanism was
removed.
