## 1. Attack simulation

Atomic Red Team test **T1560.001-4 — "Compress Data and lock with password for
Exfiltration with 7zip"**.

```
Invoke-AtomicTest T1560.001 -TestNumbers 4
```

Commands executed:

```
mkdir C:\AtomicRedTeam\atomics\T1560.001\victim-files
cd C:\AtomicRedTeam\atomics\T1560.001\victim-files
echo "This file will be encrypted" > .\encrypted_file.txt
"%ProgramFiles%\7-zip\7z.exe" u archive.7z *txt -pblue
dir
```

`u` adds/updates files in the archive; `-pblue` sets the archive password to `blue`.

**Tactic correction:** the atomic's name says "for Exfiltration", but T1560.001 is a
**Collection** technique — it covers staging and packaging data prior to exfiltration, not
the transfer itself. The rule is tagged Collection accordingly.

**Prerequisite note:** the atomic's `-GetPrereqs` installer failed with "Access is denied"
while trying to launch the downloaded 7-Zip setup. This was a prereq installation failure,
not the technique being blocked by Defender — installing 7-Zip manually resolved it and the
test then ran cleanly with exit code 0.

## 2. Telemetry validation

Each execution produces two process-creation events: `7z.exe` itself, and the `cmd.exe`
parent whose command line contains the whole chained command.

The detection query matches only the first, because the image-field anchor requires the
parameter after the PID to _be_ a 7-Zip binary. `cmd.exe` carries the 7z string later in
its command line and is correctly excluded. **One matching event per execution.**

```kql
Event
| where TimeGenerated > ago(30m)
| where Source contains "Sysmon"
| where EventCategory == 1
| where ParameterXml contains "7z"
| project TimeGenerated, ParameterXml
| order by TimeGenerated desc
```

## 3. Detection rule

Rule name: **T1560.001 – Password-Protected Archive Creation**
Severity: Medium · Run every 10 minutes · Lookback 10 minutes
Entity mapping: Host → HostName → `Computer`

```kql
Event
| where Source contains "Sysmon"
| where EventCategory == 1
| where ParameterXml matches regex @"(?i)<Param>\d+</Param><Param>[^<]*\\7z(|g|fm)\.exe</Param>"
| where ParameterXml matches regex @"(?i)\s-p\S"
```

### Design decisions

**Detect the password flag, not the archiving.** Compressing files is completely ordinary
behaviour and detecting `7z.exe` execution alone would be worthless. The attacker-relevant
signal is the **password protection**: encrypted archives defeat DLP content inspection,
email gateway scanning and network-level data classification, which is exactly why
adversaries password-protect staged data before moving it.

**`-p` must be glued to a following character.** 7-Zip takes the password inline with no
space (`-pblue`). A naive `contains "-p"` would also match `-progress`, `-p1` and other
unrelated switches. Requiring `\s-p\S` — whitespace, then `-p`, then a non-space character
— pins the match to the password form specifically.

**All three 7-Zip binaries covered.** `7z.exe` (CLI), `7zG.exe` (GUI) and `7zFM.exe` (file
manager) can all create password-protected archives. Matching only the CLI binary would
miss a user or attacker driving the GUI.

**Position-anchored image match.** As established in the T1547.001 and T1071.001 case
files, the flattened `ParameterXml` blob makes plain string matching unreliable. Anchoring
on the parameter immediately following the numeric PID pins the match to the image field.

## 4. False positive analysis

**This is the noisiest rule in this repo, and the hardest to make production-ready.**

Password-protecting an archive is normal end-user behaviour. People zip documents with a
password to email them, to share files externally, or because a policy told them to. Unlike
encoded PowerShell (rare outside management tooling) or `reg.exe` writing Run keys (rare
outside attacker tradecraft), this rule fires on an action that ordinary users take
deliberately and often.

Expected benign sources:

- Users password-protecting documents before emailing them externally
- Backup scripts creating encrypted archives
- Developers packaging builds with protected contents
- Any organisation whose own policy mandates encrypting files before transfer

### Why this signal needs correlation, not tuning

There is no field in this telemetry that distinguishes a user zipping their tax return from
an adversary staging stolen data. The command lines are identical. No amount of
string-matching refinement fixes that — the difference is **context**, not content.

The realistic production approach is to treat this as a **contributing signal** rather than
a standalone alert:

- Correlate with a large outbound transfer shortly after the archive is created
- Flag archives built from files across many user directories, or from locations the
  archiving user does not normally touch
- Weight by archive size and file count — an adversary staging a collection looks different
  from someone zipping one document
- Raise severity when the archiving process was spawned by an unusual parent

Alerting on this in isolation on a real endpoint estate would generate constant noise and
be switched off within a week. That conclusion is the finding for this technique.

## 5. Tuning — before and after

Same two-stage method as the rest of the repo.

```powershell
Invoke-AtomicTest T1560.001 -TestNumbers 4
Start-Sleep 20
Invoke-AtomicTest T1560.001 -TestNumbers 4 -Cleanup
Invoke-AtomicTest T1560.001 -TestNumbers 4
Start-Sleep 20
Invoke-AtomicTest T1560.001 -TestNumbers 4 -Cleanup
Invoke-AtomicTest T1560.001 -TestNumbers 4
```

```kql
SecurityIncident
| where CreatedTime > ago(20m)
| where Title contains "Password-Protected"
| summarize arg_max(TimeGenerated, *) by IncidentNumber
| project IncidentNumber, CreatedTime
| order by CreatedTime asc
```

### Results

|                   | Event grouping          | Alert grouping                            | Executions | Matching events | Incidents         |
| ----------------- | ----------------------- | ----------------------------------------- | ---------- | --------------- | ----------------- |
| **Before tuning** | Trigger alert per event | Disabled                                  | 3          | 3               | **3** (1177–1179) |
| **After tuning**  | All events → one alert  | Enabled, 1 day, all alerts → one incident | 3          | 3               | **1** (1184)      |

**Reduction: 3 incidents → 1 for identical attacker activity.**

### Measurement note

The first attempt at a baseline returned 1 incident from 4 matching events — the rule had
been created with event grouping already set to "Group all events into a single alert",
carried over out of habit from the previous four rules. A rule built with noise reduction
already switched on has no untuned baseline to measure against. Both levers were turned off
and the batch re-run to produce a real "before" figure.

A second timing caveat applies: with a 10-minute lookback, a new batch started within 10
minutes of the previous one re-counts the old events and inflates the baseline. Leaving a
full lookback window between batches, or filtering the count by a timestamp after the new
batch begins, avoids this.
